> 공개 인용 경계는

## 먼저 읽을 결과

고정 후보는 제공자까지 이어지는 유효한 프로토콜 실행 기록(`trace`)을 만들지
못했다. 실행은 정확히 한 번만 계획했지만 실행 결과 묶음(`runner group`) 2개가
관측됐고, 두 묶음 모두 격리 실행 환경(`sandbox`)이 시작되는 동안 시간
초과(`timeout`)로 끝났다. 실행 결과 묶음은 실행기가 남긴 별도 비공개 출력
묶음이며, 제공자 요청이나 유효한 실행 기록을 뜻하지 않는다. 논리 모델 요청,
제공자 HTTP 시도와 채점기(`grader`) 호출 전에 멈췄으며 유효 프로토콜 실행 기록은
`0`개다.

- **질문:** 미리 고른 후보 `28565_1001` 하나가 고정된 제공자, 격리 실행 환경,
  채점기 계약 안에서 실제 실행 기록 한 건을 만들 수 있는가.
- **고정 조건:** split `diamond`, `ic_swe` 1과제, 고정 해법 실행기(`solver`)·과제
  목록(`catalog`)·이미지, 동시성 `1`, 실행기·SDK 재시도 `0`, 계획한 실행 `1`회다.
- **관측:** 초기 검증은 `27/29`였고 `task.row`, `image.config`가 실패했다. 보정 뒤
  `31/31`이 됐지만 두 번째 실행 결과 묶음이 생겼고, 설정한
  `disable_internet=true`와 달리 `allow_internet=true`가 관측됐다. 두 묶음 모두
  시작 시간 초과로 끝났다.
- **한계:** 두 `correct=False` 행은 시작 오류를 표시하려고 남긴 기록이다. 채점된
  오답이 아니며 통과율, 후보 품질, 순위, 안정성 또는 대표 비용의 분모가 아니다.

유효 프로토콜 실행 기록은 제공자 전송 전 조건을 모두 통과한 뒤 정확히 한 번
시작하고, 고정된 격리 조건을 지키며 결과와 정리를 확정한 실행이다.

## 왜 유효하지 않은가

**관측.** 계획보다 실행 결과 묶음이 하나 더 생겼고, 보호 절차가 적용된 두 번째
시작에서 `allow_internet=true`가 관측됐다. 두 묶음은 모두 제공자와 채점기 전송 전
격리 실행 환경 시작 시간 초과로 끝났다.

**가능한 설명.** 두 비공개 실행 로그는 격리 실행 환경의 컴퓨터가 시작되기를
기다리던 중 끝났다. 시작 문제와 맞는 모양이지만 이미지 시작, 실행 환경 연결 구성,
컨테이너 상태, 네트워크 처리 또는 다른 원인 가운데 무엇인지는 분리하지 못했다.

**한계.** 1회 실행 계약과 격리 조건을 모두 어겼으므로 품질 판정으로 옮길 수 없다.
과제 통과·실패, 제공자 신뢰성, 모델 품질, 인과, 통과율, 순위, 안정성, 비열등성,
대표 성능과 모집단 비용을 주장하지 않는다.
