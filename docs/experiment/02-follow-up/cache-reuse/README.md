## 먼저 읽을 결과

실제 제공자 실행은 일어났지만 Cache 비교에 쓸 유효 사이클은 만들어지지 않았다.
첫 사이클 하나를 시도했고 그 사이클이 무효가 되어 유효 사이클은 `0`개다. 따라서
Cache 효과, 캐시 미스율, 절감액, 재사용 대비와 안정성은 계산하지 않았다.

이 문서에서 실행 묶음(`bundle`)은 조건 하나와 재사용 수준 하나에서 고정 과제를
실행한 단위다. 과제 실행(`task trial`)은 그 안에서 과제 하나를 실행한 기록이다.
요청 접두부(`request prefix`)는 개별 요청의 직렬화된 메시지 내용 안에서 앞부터
비교하는 부분이다. 과제와 논리 요청 순번은 재사용 단계 사이에서 어떤 개별 요청을
서로 비교할지 정하며, 요청들의 열 자체가 접두부는 아니다. 요청 개수·순번과
바이트 또는 토큰 단위의 접두부 길이는 서로 다른 값이다.

- **질문:** 같은 과제의 앞선 재사용 실행과 요청 접두부를 맞추면서 `none`과
  `squeez`를 비교할 유효 사이클을 확보할 수 있는가.
- **고정 조건:** `{none, squeez}` × 재사용 수준 `{0, 1, 2}`를 계획했고, 순서는
  `0 → 1 → 2`로 정했다. 셀마다 고정 5과제, 동시성 `1`, 초기 계획은 10개 유효
  사이클이었다.
- **관측:** 사이클 `1`개를 시도해 `1`개가 무효였다. 제공자 호출 `18`회와 완결된
  과제 실행의 판정 `3/5`는 이 불완전한 무효 사이클의 설명값이다.
- **한계:** 캐시 비교의 분모는 `0`이다. 조건 효과, 일반 품질, 인과, 순위,
  비열등성 또는 총절감을 주장할 수 없다.

유효 사이클은 두 조건과 세 재사용 수준의 여섯 실행 묶음이 모두 끝나고 요청
접두부, 사용량, 출처, 실행 조건을 통과한 사이클이다.

## 실행 분모와 중단 흐름

## 사이클이 멈춘 이유

**관측.** `none`, 재사용 `0` 실행 묶음은 끝났다. 이어진 `none`, 재사용 `1`의
`cancel-async-tasks`가 논리 요청 순번(`ordinal`) `3`에 도달했지만 같은 과제의
재사용 `0` 실행에는 요청이 `2`개뿐이었다. 따라서 순번 `3`에서 비교할 선행 요청이
없었다. 존재하지 않는 요청 쌍의 접두부 차이나 길이를 잰 것이 아니라, 요청 접두부
검증이 현재 순번 `3` 요청을 제공자 전송 전에 거부했다. 사이클은 무효로 보존했고
실행 전체 재시도(`outer retry`)와 대체 실행은 수행하지 않았다.

**가능한 설명.** 두 과제 실행이 서로 다른 요청 수를 만들었다. 비결정적 실행
경로라면 이런 모양이 나올 수 있지만 이번 실행은 그 설명을 시험하지 않았다.

**한계.** 여기서 달라진 것은 토큰이나 바이트의 폭이 아니라 요청 개수다. 요청
개수가 달라진 원인을 모델, 과제, 전송 계층, 격리 이름공간, 압축 또는 다른 기제로
분리하지 못했다. 유효 사이클이 `0`개이므로 Cache 비교와 안정성 연장은 실행되지
않았다.
