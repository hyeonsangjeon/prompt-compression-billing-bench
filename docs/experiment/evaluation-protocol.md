# 압축 평가 규약 설계안

**상태:** 실행 전 설계안이다. 평가 0회다. 평가 적격은 20개 유효 결과 중 18회 이상 통과로 정했고 D1과 F1-R1을 채택했다. 행렬, 성공 기준과 task 군집을 반영한 `R(K)` 계산식은 승인되지 않았다. 선별과 평가를 모두 실행한다고 확정한 계획이 아니며, 선별 뒤 전체 적격 과제 `K`개의 일정 gate를 통과하고 별도 승인을 받아야 평가로 진행한다.

## 평가가 답할 질문

Terminal-Bench 2.1의 평가 적격 과제에서 우리 harness가 식별한 로그 출력만 바꿀 때, 고정한 각 압축기가 허용한 품질 저하 안에서 end-to-end 비용을 줄이는가를 묻는다.

품질 기준을 넘겨 나빠지면 token이 줄어도 도입하지 않는다. 품질 기준을 통과한 조건만 비용 절감 기준을 판단한다. 어느 조건도 두 기준을 함께 통과하지 못하면 이 모집단·모델·프로필에서는 도입 근거가 없다고 기록한다. 가설이 틀린 것도 결과다.

## 비교 행렬 제안 M1

위치는 네 조건 모두 `identified_log_spans`, 즉 현재 분류기가 식별한 로그 성격의 명령 출력으로 고정한다. 구조화 출력, 파일 읽기, 코드, 지시문과 assistant 이력은 보호한다.

| 조건 | 도구·버전 | 고정 프로필 | 위치 | 실제 개입 | 성격 |
| --- | --- | --- | --- | --- | --- |
| `none` | 없음 | 추가 압축 없음 | 동일 후보를 관측만 함 | 동시 대조군 | 설계안 |
| `squeez` | squeez `1.48.4` | `wrap_cat_input_txt`, fresh state, 앞 30개 내용 줄 뒤 삭제 | `identified_log_spans` | 버리기·손실 | 설계안 |
| `headroom` | Headroom `0.36.5` | paths-only profile revision 2, exact inverse 확인 | `identified_log_spans` | 공통 경로 접두어 묶기 | 설계안 |
| `llmlingua2` | LLMLingua-2 `0.2.2` | `rate=0.5`, 모델 revision `ebaba9b0e874dadd3003ffcff828e4397e568089`, CPU float32, 입력 앞 5,000자만 처리 | `identified_log_spans` | 앞 5,000자의 token 선택과 뒤쪽 삭제가 함께 있는 손실 개입 | 설계안 |

현재 live adapter는 LLMLingua-2에 넘길 후보가 5,000자를 넘으면 앞 5,000자만 압축하고 뒤쪽을 버린다. 기존 `none` 100 trial에서 식별된 후보 79출현 중 31출현이 이 경계를 넘었다. **성격:** 비공개 기준선 원본의 분류 집계·현재 구현 확인. 따라서 M1 그대로 실행하면 LLMLingua-2의 token 선택만이 아니라 입력 한도에 따른 삭제까지 묶인 프로필을 평가한다.

승인 선택지는 두 가지다. 현재 복합 프로필을 그대로 평가하되 결과를 LLMLingua-2 자체 효과로 분해하지 않거나, 뒤쪽을 버리지 않는 새 profile을 구현한 뒤 정적 보존 검사와 시간을 다시 재는 것이다. 아래 일정은 현재 복합 프로필을 가정한 계산이며 어느 선택지도 아직 확정하지 않는다.

Headroom `0.37.0` `coding` 프로필은 이번 M1에 넣지 않는다. 그 프로필은 툴 제외, 파일 읽기·분석 문맥 보호, AST 기반 코드 압축과 turn 간 중복 제거를 함께 바꾸므로 현재 질문에서는 압축기와 위치 선정 로직이 동시에 움직인다. 별도 제품 프로필 평가가 필요하며, paths-only 결과를 `coding` 프로필 전체의 결과로 일반화하지 않는다.

구조화 출력과 파일 읽기로 위치를 넓히는 조건도 M1에서 제외한다. 이번에는 도구만 바꾸고 위치는 고정한다. 위치 확대는 같은 도구·버전·프로필을 고정한 별도 행렬로 승인받아야 한다.

## block randomization

하나의 block은 `task × repetition`이며 네 조건을 각각 한 번 포함한다. block 안 조건 순서는 `[seed, block ID, condition]`을 공백 없는 UTF-8 JSON 배열로 직렬화한 SHA-256 값의 오름차순으로 정하고, 동률이면 condition 이름순으로 정한다. 실행 manifest는 완전한 block 단위로 이 순서를 이어 붙인다. 동시성 8에서는 처음에 block 두 개까지 시작하고, 이후에는 한 trial이 끝날 때 manifest의 다음 trial을 시작한다. 실행 중인 조건 수는 처리 시간에 따라 달라질 수 있으므로 통제됐다고 주장하지 않고 계획 순서와 실제 시작 순서를 둘 다 남긴다.

선별의 `none`은 과제 선택 자료일 뿐이다. 평가는 각 block의 contemporaneous `none`을 사용한다. pause·resume 뒤 완료된 trial은 다시 실행하지 않고, 실패한 attempt를 재시도하면 같은 trial ID 아래 새 attempt ID와 provider request ID를 부여한다.

## 지표와 판정 순서

1. **주지표·품질 gate:** 과제별 pass-rate 차이를 먼저 본다. 조건 `c`의 주지표는 `과제별(pass-rate_c - pass-rate_none)`를 과제에 같은 가중치로 평균한 값이다. 호출 수가 많은 과제가 더 큰 가중치를 갖지 않는다.
2. **도입 이득:** 품질 gate를 통과한 조건에서 계획된 trial당 end-to-end 계산 비용의 감소를 본다. provider 입력·cached input·출력 token 비용, 실제 retry 비용과 실행 VM 시간을 포함한다. 실패 trial에서 발생한 비용도 빼지 않는다. 단가가 빠지면 부분 비용으로 표시하고 도입 결론을 내리지 않는다.
3. **설명 지표:** provider 입력·출력 token, cached input token, 총 호출 수, turn 수, 같은 명령 재실행, 벽시계, 압축 시간과 실패 유형을 따로 제시한다.

입력 token만 줄고 출력 token·호출 수·재실행·시간 또는 총비용이 늘면 비용 절감으로 판정하지 않는다.

`wrong_answer`와 `wrong_format`은 모두 품질 실패로 계산한다. 실패 category, verifier test ID, 전후반 통과 수와 실패 순서는 진단 지표로 기록하지만 과제를 주분석에서 제외하거나 성공 문턱을 바꾸는 데 쓰지 않는다.

## 성공 기준 후보

아래 품질 허용폭과 최소 비용 절감은 모두 **임의의 설계값이며 승인 전 후보**다. 통계 계산은 세 압축기와 `none`의 세 비교에 Holm 보정을 적용할 때의 가장 작은 단측 유의수준 `0.05÷3`, 검정력 80%, 평가 적격 pass 확률 0.80을 가정한 trial-level 민감도 계산이다.

품질 계산은 같은 task×반복의 두 조건 결과가 pass 확률 0.80에서 서로 독립이라고 가정해 짝 안의 불일치 확률을 `2×0.8×0.2=0.32`로 두었다. 조건당 필요 trial은 `ceil(0.32×(z(1-0.05/3)+z(0.8))²÷허용폭²)`로 계산했다. 비용 계산은 기존 목적 선정 5과제×20회의 provider usage 기반 계산 비용 변동계수 0.525933, 조건 간 비용 상관 0을 가정해 `ceil(2×0.525933²×(z(1-0.05/3)+z(0.8))²÷최소 절감²)`를 사용했다. 여기서 `z`는 표준정규분포 분위수이며 두 식 모두 정규 근사다. 비용 식은 실제 절감이 표의 최소 절감과 같을 때 절감 0과 구분하는 경우를 계산한다.

짝 안의 실제 불일치, VM·저장 비용을 포함한 end-to-end 비용 분산, task별 이질성과 시간대 상관은 아직 없다. 비용 표본 수에 쓴 변동계수는 제공자 usage 기반 계산 비용만 반영한다. 특히 283·488·1,129는 trial을 분석 단위로 둔 민감도 계산값이며, task 안 반복의 군집과 과제 간 이질성을 반영한 최종 표본 수가 아니다. 따라서 아래 수는 이 가정에서 나온 계산값이지 통계적 하한이나 충분성의 증명이 아니다.

비용의 최종 목표는 provider usage 기반 비용만이 아니라 실제 retry 비용과 VM 실행 비용을 포함한다. 그러나 217·488의 비용 민감도 계산은 기존 provider usage 기반 계산 비용의 변동계수만 사용했다. VM 비용 분산을 포함한 최종 표본 수로 읽으면 안 된다.

균형 잡힌 `K`과제×`R`반복에서 압축 조건의 추가 실패 trial 1건은 그 과제의 pass-rate 차이를 `100÷R`%p, 과제 동일 가중 전체 평균을 `100÷(K×R)`%p 움직인다. 과제 하나가 통째로 나빠지는 것은 전체 평균에서 `1÷K`의 가중치를 갖는다. 따라서 “품질 하락 1건”은 trial 1건인지 과제 1개인지 함께 써야 하며, 488을 488개의 독립 과제나 최종 품질 분모로 읽지 않는다.

S1은 추천안이 아니라 15과제를 넣어 일정을 비교한 시나리오다. S1의 10%p와 15%는 업무 합의나 과거 효과에서 도출한 값이 아니며, 품질 보호와 일정의 관계를 보기 위해 둔 임의값이다. S2는 비용 문턱을 10%로 낮추는 대신 품질 저하를 15%p까지 허용하며, trial-level 비용 분산 가정에서는 S1보다 큰 값이 나온다. S3는 품질 저하를 5%p로 좁히며 같은 계산에서 1,129 trial/조건이 나온다. 세 후보 중 하나를 선별 결과 전에 승인하며 이 값들만으로 최종 task 수와 반복 수를 정하지 않는다.

품질은 Holm 보정한 단측 신뢰구간의 하한이 승인한 음의 허용폭보다 클 때만 gate를 통과한다. 비용은 절감 점추정이 표의 최소 절감 이상이고 같은 보정의 단측 신뢰구간 하한이 0보다 클 때 도입 이득을 통과한다. 최소 절감 자체를 신뢰구간 하한으로 요구하려면 기대 절감값을 별도로 가정해 표본 수를 다시 계산해야 한다.

최종 구간은 task를 층으로 두고 각 task 안의 반복 block을 다시 뽑는 짝지은 bootstrap으로 계산한다. task 수가 적어 이 방법도 불안정하면 작은 표본으로 확정하지 않고 판정 불가로 남긴다. 관측 차이만 허용폭 안에 있다고 성공으로 쓰지 않는다.

S1·S2·S3 중 하나와 task 군집 계산 방법은 선별 결과를 보기 전에 승인하고 이후 바꾸지 않는다. 선별 결과가 나온 뒤 확정하는 값은 평가 적격 과제 수 `K`뿐이다. 반복 수는 사전 승인한 `R(K)` 식에 `K`를 대입해 정하며, 일정에 맞추려고 성공 기준이나 식을 바꾸지 않는다.

## task 군집과 반복 수 공식 — 승인 대기

아래 식은 task 안 반복을 독립 trial로 세지 않기 위한 **공식 후보**다. `N_quality,S`와 `N_cost,S`는 선택한 S1·S2·S3의 trial-level 계산값이다. `ρ_quality`와 `ρ_cost`는 같은 task 안 paired 품질 차이와 비용 차이의 지표별 군집 상관이다.

```text
N_eff,m(K, R, ρ_m) = K × R ÷ [1 + (R - 1) × ρ_m]
R_S(K) = min{r ∈ 양의 정수 :
  N_eff,quality(K, r, ρ_quality) ≥ N_quality,S 이고
  N_eff,cost(K, r, ρ_cost) ≥ N_cost,S}
```

S 후보와 두 `ρ`의 값·근거·추정 방법은 선별 결과를 보기 전에 승인해야 한다. 현재 두 `ρ`의 근거가 없어 임의의 값을 넣지 않았다. 어느 지표든 `K ≤ N_m,S×ρ_m`이면 반복을 늘려도 위 식을 충족할 수 없으므로 자동으로 과제를 일부 고르거나 기준을 낮추지 않고 중단해 승인을 요청한다. 이 식은 지표별 군집 상관으로 과제 간 이질성을 나타내는 근사이므로, 채택하더라도 최종 분석은 task 동일 가중 paired bootstrap과 task별 효과 분포를 함께 제시한다.

283·488·1,129는 이 식의 지표별 `N_m,S`를 만드는 trial-level 민감도 계산일 뿐이다. 두 `ρ`와 `K`를 반영하기 전에는 최종 표본 수가 아니다. 15과제×19·33·76회도 일정 비교 예시이며 최종 상한이 아니다.

## 최종 과제 수와 일정 gate

선별 전에 평가 적격 과제 수를 추정하지 않는다. 선별이 끝나면 기준 B를 통과한 전체 과제 수를 `K`로 두고, 사전 승인한 `R_S(K)`를 적용한다. 유형 분포, 통과율, 실패 위치·category·test ID를 기준으로 일부를 자동 선정하지 않는다.

전체 `K`개 평가의 P90과 Blob 검증·replay·분석·보고 여유가 실제 남은 시간 안에 들어오면 전부 평가한다. 들어오지 않으면 평가를 시작하지 않고 범위 변경 승인을 요청한다. 이 gate는 선별 결과에 따라 평가를 중단할 수 있게 하지만, 성공 기준이나 표본 공식을 사후 변경할 권한은 주지 않는다.

native 투영은 [선별 시간](screening-protocol.md#선별-시간-계산)과 같은 식을 썼다. 두 번의 8동시 software preflight에서 squeez와 Headroom의 후보 8출현 처리 구간은 각각 0.21초를 넘지 않았다. 기존 0.79출현/trial을 그대로 적용하면 가장 큰 표의 경로에서도 두 도구 합계가 0.02시간보다 작아 표의 소수 둘째 자리에는 더하지 않았다. 이는 새 과제에서 후보 발생량이 같다는 계산 조건이지 전체 평가의 측정값이 아니다.

LLMLingua-2 지연은 기존 0.79출현/trial과 5,000자 호출 시간을 새 과제에도 옮기고, 후보 호출을 8개씩 빈틈없이 처리할 수 있다고 가정한 값이다. 과거 79출현 중 31출현이 5,000자를 넘었고 과제별 후보 비중도 달랐으므로 새 선별 과제의 실제 시간은 이 값과 달라질 수 있다. worker 초기화, 후보 도착 간격, image 최초 pull, retry와 한 trial 안에서 후보가 몰려 공통 timeout에 닿는 경우도 포함하지 않았다. 조건별 timeout은 바꾸지 않으며, 압축 지연으로 난 timeout도 해당 조건의 결과로 센다.

### 마감과 보고 여유

최종 마감은 `2026-09-17 21:00 KST`다. 2026-09-14 날짜 기준으로 약 80시간이 남아 전체 계획은 시간상 가능해 보이지만, 전체 89과제의 P90 범위를 확인하기 전까지 이 판단은 잠정이다. 실행 종료 목표는 `2026-09-17 09:00 KST`이며, 그 뒤 12시간을 Blob 무결성 확인, replay 확인, 분석과 보고에 남긴다. 이 12시간은 과거 측정이나 작업량 추정에서 도출하지 않은 **임의의 운영 여유**다.

아래 표는 일정 민감도를 보기 위해 평가 과제를 15개로 가정하고, 그 뒤 평가 실행을 별도로 승인받는 경우만 계산한다. 15과제는 최종 표본 수나 상한이 아니다. 선별에서 평가 중단 gate가 걸리면 평가 시간은 발생하지 않는다.

선별 6.77·8.31시간은 89과제×최대 20회 전체를 계산했고 조기 종료를 반영하지 않았다. 평가 시간은 15과제 일정 시나리오만 포함한다. 두 실행 시간에는 각 native trial 안의 내장 verifier가 포함되지만, image 최초 준비, 전체 모집단 setup 꼬리, retry, 선별 결과 검토와 승인 대기, scheduler 구현, Blob 원격 hash 대조와 replay 검증은 포함되지 않는다. 뒤의 검증·분석·보고에는 임의의 운영 여유 12시간을 별도로 예약했지만 이 값은 측정 P90이 아니다.

기존 27.74시간은 표에 표시한 두 자리 수를 먼저 더한 값이다. 반올림 전 산식으로 다시 계산하면 B+S1은 실행 P90 15.7465시간이고, 별도 12시간을 더한 값은 27.7465시간이므로 두 자리 표기는 27.75시간이다. 이 값도 전체 89과제 P90을 확인하기 전에는 잠정 투영이다.

12시간 자체와 이를 검증·분석·보고에 나누는 비율에는 측정 근거가 없다. `6시간+6시간`과 검증을 우선한 `8시간+4시간`은 모두 임의의 운영 후보이며 승인 전에는 확정하지 않는다. workspace replay는 실행 시간 투영에는 없고 이 공동 예약에만 들어 있다.

실제 일정은 다음 산식으로 계산한다. `K`는 선별 뒤 확인한 전체 평가 적격 과제 수, `R`은 선별 전에 승인한 식으로 계산한 `R_S(K)`, 조건 수는 현재 M1의 4개다.

```text
선별 native 시간(q) = ceil(실제 계획 선별 trial ÷ 8) × none trial 시간(q) × 1.4345
평가 native 시간(q) = ceil(K × R × 4 ÷ 8) × none trial 시간(q) × 1.4345
LLMLingua-2 지연(q) = ceil(K × R × 0.79 ÷ 8) × 5,000자 동시 8호출 시간(q)
retry 0회 실행(q) = 선별 native + 평가 native + LLMLingua-2 지연
준비 retry 최대 증가분(q) = ceil(1,780 ÷ 8) × Tprep(q) + ceil(4 × K × R ÷ 8) × Tprep(q)
최악 실행(q) = retry 0회 실행(q) + 준비 retry 최대 증가분(q)
마감 gate 시간(q) = 선택한 실행 경로(q) + 임의의 운영 여유 12시간
```

여기서 q는 P50 또는 P90이고, `Tprep(q)`는 동시성 8에서 provider 호출 전에 실패한 준비 attempt의 벽시계 분위수다. 이 값은 아직 측정하지 않아 준비 retry 최대 증가분과 최악값을 숫자로 제시할 수 없다. 최대 retry 수는 선별 1,780회와 평가 `4×K×R`회다. 모든 첫 attempt가 준비 단계에서 실패하고 fresh 환경의 두 번째 attempt를 시작하는 경계값이며, 품질 실패나 provider 호출 뒤 오류에는 적용하지 않는다.

| 일정 구분 | 조기 종료 | 준비 retry | 현재 제시 가능한 값 |
| --- | --- | --- | --- |
| retry 0회 | 가정하지 않음 | 0회 | 선별 P50 6.7662시간·P90 8.3136시간과 위 `K`, `R` 평가식 |
| 준비 retry 최대 증가분 | 해당 없음 | 선별 1,780회 + 평가 `4KR`회 | `Tprep50`·`Tprep90` 미측정으로 식만 제시 |
| 최악값 | 없음 | 모든 계획 trial에서 F1-R1 1회 | retry 0회 + 최대 증가분. 마감 gate에서는 임의의 운영 여유 12시간을 별도로 더함 |

D1은 진단 기록만 추가하므로 계획 trial 수를 바꾸지 않는다. F1-R1은 준비 오류가 있을 때만 attempt 수와 경과 시간·비용을 늘린다. 조기 종료를 반영한 사후 실제 시간은 완료 trial과 시작된 attempt로 집계하되, 선별 전 일정 적합 판단에는 조기 종료 절감을 가정하지 않는다. 압축기 수나 프로필이 바뀌면 조건 수와 해당 압축 지연 항을 함께 바꾼다.

승인 gate 사이의 대기 시간은 표에 없다. 기준 B를 통과해도 평가 행렬·표본 수·예상 종료 시각을 다시 승인하기 전에는 평가를 시작하지 않는다.

시간이 부족하면 결과를 본 뒤 과제나 반복을 빼지 않는다. S1·S2·S3 선택과 `R(K)` 식은 선별 전에 승인하고 이후 바꾸지 않는다. 선별 뒤 전체 `K`개 평가의 P90과 임의의 운영 여유 12시간이 마감에 맞지 않으면 평가를 중단하고 승인을 요청한다. 압축기 조건을 줄이려면 선별 전 별도 범위 변경 승인이 필요하고, 조건별 반복 수를 다르게 줄이지 않는다. 89과제 선별 모집단, contemporaneous `none`과 증거 계약은 유지한다.
