# 압축 평가 규약 설계안

**상태:** 실행 전 설계안이다. 평가 0회다. 평가 적격은 20개 유효 결과 중 18회 이상 통과로 정했고 D1과 F1-R1을 채택했다. 행렬, 성공 기준, 비용 분석 경로, `rho_quality`·`rho_cost`의 사전 범위와 `R(K, rho)` 계산식은 승인되지 않았다. 선별과 평가를 모두 실행한다고 확정한 계획이 아니며, 선별 뒤 전체 적격 과제 `K`개의 일정 gate를 통과하고 별도 승인을 받아야 평가로 진행한다.

## 평가가 답할 질문

Terminal-Bench 2.1의 평가 적격 과제에서 우리 harness가 식별한 로그 출력만 바꿀 때, 고정한 각 압축기가 허용한 품질 저하 안에서 end-to-end 비용을 줄이는가를 묻는다.

품질 기준을 넘겨 나빠지면 token이 줄어도 도입하지 않는다. 품질 기준을 통과한 조건만 비용 절감 기준을 판단한다. 어느 조건도 두 기준을 함께 통과하지 못하면 이 모집단·모델·프로필에서는 도입 근거가 없다고 기록한다. 가설이 틀린 것도 결과다.

## 비교 행렬 제안 M1

위치는 네 조건 모두 `identified_log_spans`, 즉 현재 분류기가 식별한 로그 성격의 명령 출력으로 고정한다. 구조화 출력, 파일 읽기, 코드, 지시문과 assistant 이력은 보호한다.

| 조건 | 도구·버전 | 고정 프로필 | 위치 | 실제 개입 | 성격 |
| --- | --- | --- | --- | --- | --- |
| `none` | 없음 | 추가 압축 없음 | 동일 후보를 관측만 함 | 동시 대조군 | 설계안 |
| `squeez` | squeez `1.48.4` | `wrap_cat_input_txt`, fresh state, 앞 30개 내용 줄 뒤 삭제 | `identified_log_spans` | 버리기·손실 | 설계안 |
| `headroom` | Headroom `0.36.5` | paths-only profile revision 2, exact inverse 확인 | `identified_log_spans` | 공통 경로 접두어 묶기 | 설계안 |
| `llmlingua2` | LLMLingua-2 `0.2.2` | `rate=0.5`, 모델 revision `ebaba9b0e874dadd3003ffcff828e4397e568089`, CPU float32, 입력 앞 5,000자만 처리 | `identified_log_spans` | 앞 5,000자의 token 선택과 뒤쪽 삭제가 함께 있는 손실 개입 | 설계안 |

현재 live adapter는 LLMLingua-2에 넘길 후보가 5,000자를 넘으면 앞 5,000자만 압축하고 뒤쪽을 버린다. 기존 `none` 100 trial에서 식별된 후보 79출현 중 31출현이 이 경계를 넘었다. **성격:** 비공개 기준선 원본의 분류 집계·현재 구현 확인. 따라서 M1 그대로 실행하면 LLMLingua-2의 token 선택만이 아니라 입력 한도에 따른 삭제까지 묶인 프로필을 평가한다.

승인 선택지는 두 가지다. 현재 복합 프로필을 그대로 평가하되 결과를 LLMLingua-2 자체 효과로 분해하지 않거나, 뒤쪽을 버리지 않는 새 profile을 구현한 뒤 정적 보존 검사와 시간을 다시 재는 것이다. 아래 일정은 현재 복합 프로필을 가정한 계산이며 어느 선택지도 아직 확정하지 않는다.

Headroom `0.37.0` `coding` 프로필은 이번 M1에 넣지 않는다. 그 프로필은 툴 제외, 파일 읽기·분석 문맥 보호, AST 기반 코드 압축과 turn 간 중복 제거를 함께 바꾸므로 현재 질문에서는 압축기와 위치 선정 로직이 동시에 움직인다. 별도 제품 프로필 평가가 필요하며, paths-only 결과를 `coding` 프로필 전체의 결과로 일반화하지 않는다.

구조화 출력과 파일 읽기로 위치를 넓히는 조건도 M1에서 제외한다. 이번에는 도구만 바꾸고 위치는 고정한다. 위치 확대는 같은 도구·버전·프로필을 고정한 별도 행렬로 승인받아야 한다.

## block randomization

하나의 block은 `task × repetition`이며 네 조건을 각각 한 번 포함한다. block 안 조건 순서는 `[seed, block ID, condition]`을 공백 없는 UTF-8 JSON 배열로 직렬화한 SHA-256 값의 오름차순으로 정하고, 동률이면 condition 이름순으로 정한다. 실행 manifest는 완전한 block 단위로 이 순서를 이어 붙인다. 동시성 8에서는 처음에 block 두 개까지 시작하고, 이후에는 한 trial이 끝날 때 manifest의 다음 trial을 시작한다. 실행 중인 조건 수는 처리 시간에 따라 달라질 수 있으므로 통제됐다고 주장하지 않고 계획 순서와 실제 시작 순서를 둘 다 남긴다.

선별의 `none`은 과제 선택 자료일 뿐이다. 평가는 각 block의 contemporaneous `none`을 사용한다. pause·resume 뒤 완료된 trial은 다시 실행하지 않고, 실패한 attempt를 재시도하면 같은 trial ID 아래 새 attempt ID와 provider request ID를 부여한다.

## 지표와 판정 순서

1. **주지표·품질 gate:** 과제별 pass-rate 차이를 먼저 본다. 조건 `c`의 주지표는 `과제별(pass-rate_c - pass-rate_none)`를 과제에 같은 가중치로 평균한 값이다. 호출 수가 많은 과제가 더 큰 가중치를 갖지 않는다.
2. **도입 이득:** 품질 gate를 통과한 조건에서 계획된 trial당 end-to-end 계산 비용의 감소를 본다. provider 입력·cached input·출력 token 비용, 실제 retry 비용과 실행 VM 시간을 포함한다. 실패 trial에서 발생한 비용도 빼지 않는다. 단가가 빠지면 부분 비용으로 표시하고 도입 결론을 내리지 않는다.
3. **설명 지표:** provider 입력·출력 token, cached input token, 총 호출 수, turn 수, 같은 명령 재실행, 벽시계, 압축 시간과 실패 유형을 따로 제시한다.

입력 token만 줄고 출력 token·호출 수·재실행·시간 또는 총비용이 늘면 비용 절감으로 판정하지 않는다.

`wrong_answer`와 `wrong_format`은 모두 품질 실패로 계산한다. 실패 category, verifier test ID, 전후반 통과 수와 실패 순서는 진단 지표로 기록하지만 과제를 주분석에서 제외하거나 성공 문턱을 바꾸는 데 쓰지 않는다.

## 성공 기준 후보

아래 품질 허용폭과 최소 비용 절감은 모두 **임의의 설계값이며 승인 전 후보**다. 통계 계산은 세 압축기와 `none`의 세 비교에 Holm 보정을 적용할 때의 가장 작은 단측 유의수준 `0.05÷3`, 검정력 80%, 평가 적격 pass 확률 0.80을 가정한 trial-level 민감도 계산이다.

품질 계산은 같은 task×반복의 두 조건 결과가 pass 확률 0.80에서 서로 독립이라고 가정해 짝 안의 불일치 확률을 `2×0.8×0.2=0.32`로 두었다. 조건당 필요 trial은 `ceil(0.32×(z(1-0.05/3)+z(0.8))²÷허용폭²)`로 계산했다. 비용 계산은 기존 목적 선정 5과제×20회의 provider usage 기반 계산 비용 변동계수 0.525933, 조건 간 비용 상관 0을 가정해 `ceil(2×0.525933²×(z(1-0.05/3)+z(0.8))²÷최소 절감²)`를 사용했다. 여기서 `z`는 표준정규분포 분위수이며 두 식 모두 정규 근사다. 비용 식은 실제 절감이 표의 최소 절감과 같을 때 절감 0과 구분하는 경우를 계산한다.

짝 안의 실제 불일치, VM·저장 비용을 포함한 end-to-end 비용 분산, task별 이질성과 시간대 상관은 아직 없다. 비용 표본 수에 쓴 변동계수는 제공자 usage 기반 계산 비용만 반영한다. 특히 283·488·1,129는 trial을 분석 단위로 둔 민감도 계산값이며, task 안 반복의 군집과 과제 간 이질성을 반영한 최종 표본 수가 아니다. 따라서 아래 수는 이 가정에서 나온 계산값이지 통계적 하한이나 충분성의 증명이 아니다.

비용의 최종 목표는 provider usage 기반 비용만이 아니라 실제 retry 비용과 VM 실행 비용을 포함한다. 그러나 217·488의 비용 민감도 계산은 기존 provider usage 기반 계산 비용의 변동계수만 사용했다. VM 비용 분산을 포함한 최종 표본 수로 읽으면 안 된다.

균형 잡힌 `K`과제×`R`반복에서 압축 조건의 추가 실패 trial 1건은 그 과제의 pass-rate 차이를 `100÷R`%p, 과제 동일 가중 전체 평균을 `100÷(K×R)`%p 움직인다. 과제 하나가 통째로 나빠지는 것은 전체 평균에서 `1÷K`의 가중치를 갖는다. 따라서 “품질 하락 1건”은 trial 1건인지 과제 1개인지 함께 써야 하며, 488을 488개의 독립 과제나 최종 품질 분모로 읽지 않는다.

S1은 추천안이 아니라 15과제를 넣어 일정을 비교한 시나리오다. S1의 10%p와 15%는 업무 합의나 과거 효과에서 도출한 값이 아니며, 품질 보호와 일정의 관계를 보기 위해 둔 임의값이다. S2는 비용 문턱을 10%로 낮추는 대신 품질 저하를 15%p까지 허용한다. S3는 품질 저하를 5%p로 좁히고 비용 문턱은 S1과 같은 15%로 둔다. 세 후보 중 하나를 선별 결과 전에 승인하며, 일정에 맞는 후보를 고르거나 이 값들만으로 최종 task 수와 반복 수를 정하지 않는다.

| S2 | 평균 품질 저하를 최대 15%p까지 허용해 10% 비용 절감도 도입 후보로 검토한다 | 세 후보 중 가장 큰 평균 품질 저하를 허용한다. 과제별 큰 손상과 10%보다 작은 비용 절감은 잡지 못한다 | 임의 기준의 해석 |

세 기준은 모두 과제 동일 가중 평균을 판정하므로 특정 과제의 큰 손상을 평균이 가릴 수 있다. task별 차이 분포와 실패 category·test ID는 이 한계를 보여주는 진단 지표이며, 사후에 과제를 빼거나 성공 기준을 바꾸는 용도로 쓰지 않는다. 원하는 품질 허용폭과 비용 절감 문턱이 승인된 `rho` 범위와 실제 `K`에서 판별되지 않거나 일정에 들어오지 않으면 기준을 자동으로 완화하지 않고 **현재 일정에서 판별 불가**로 보고한다.

품질은 Holm 보정한 단측 신뢰구간의 하한이 승인한 음의 허용폭보다 클 때만 gate를 통과한다. 비용은 절감 점추정이 표의 최소 절감 이상이고 같은 보정의 단측 신뢰구간 하한이 0보다 클 때 도입 이득을 통과한다. 최소 절감 자체를 신뢰구간 하한으로 요구하려면 기대 절감값을 별도로 가정해 표본 수를 다시 계산해야 한다.

### 비용 기대 절감값 선택지 — 승인 대기

[압축기 정적 측정](compressors.md#정적-크기)의 squeez 14.1366%, Headroom 0.1976%, LLMLingua-2 11.6306%는 식별된 후보 구간만 바꾼 뒤 저장 요청 56개의 전체 message content 242,937 `o200k_base` token을 분모로 다시 센 로컬 입력 token 감소율이다. **표본·분모:** 목적 선정 5과제·과거 15실행·저장 요청 56개, 후보 107출현·27고유 입력. **성격:** 모델 호출 없는 정적 측정·계산이며 제공자 청구 token이나 end-to-end 총비용 측정이 아니다.

이 정적 감소율은 같은 표본과 프로필에서 입력 token 감소의 참고 상한으로만 쓴다. 출력 token, cache, 호출 수, 재실행, retry와 VM 비용을 설명하지 못하므로 총비용 기대효과나 비용 검정력 식의 효과크기로 직접 대입하지 않는다. 이 저장소 밖에서 전달된 한 관측에서는 압축 조건의 bash 출력량이 기준보다 117% 많았지만, 계산 단위·표본 분모와 원 출처는 이 저장소에 등록되지 않았고 여기서 재측정하지 않았다. 이 관측만으로 증가 원인을 압축으로 확정하지 않지만, 입력 감소율을 총비용 감소율로 치환할 수 없다는 한계를 보여준다.

| 처리 방법 | 사전에 두는 값 | 얻는 것 | 잃는 것·판정 범위 | 상태·성격 |
| --- | --- | --- | --- | --- |
| 전체 요청 정적 감소율을 입력 참고 상한으로만 사용 | 위 세 로컬 입력 token 감소율 | 실제 고정 표본에서 후보 변환 뒤의 입력 크기를 설명 | 총비용 기대값이 없으므로 비용 gate의 최종 표본 수와 검정력을 정하지 못함 | 측정 참고값·단독 채택 불충분 |
| 임의의 기대 절감 범위로 검정력 민감도 계산 | `Delta_cost = C_min + g`, 임의 후보 `g=2.5·5·10%p` | 기대 총비용 절감이 도입 문턱보다 얼마나 큰지에 따라 필요 표본 수와 판정 불가 위험이 어떻게 바뀌는지 계산 | 범위는 실측 근거가 없고 결과를 예측하지 않음. 승인 뒤에도 민감도 계획값일 뿐 관측값이 아님 | 임의 후보·승인 대기 |
| 비용은 기술통계만 보고 | 기대 절감값 없음 | 근거 없는 효과크기와 검정력 주장을 피하고 실제 비용 분포를 그대로 제시 | 비용 도입 gate를 통과했다고 결론 내릴 수 없으며 비용 결론은 판정 불가 | 범위 변경 후보·승인 대기 |

`C_min`은 S1·S3의 15% 또는 S2의 10% 최소 절감 문턱이고, `Delta_cost`는 아직 관측하지 않은 진짜 end-to-end 총비용 절감이다. 두 번째 방법의 `g` 범위와 격자는 자료에서 도출하지 않은 임의값이다. 이를 승인하면 기존 provider usage 변동계수 근사에서 다음 식으로 **두 비용 조건을 함께 통과할 검정력**을 민감도로 계산할 수 있다.

```text
SE_cost(N_eff) = sqrt(2 × 0.525933² / N_eff)
cost_gate_threshold = max(C_min, z(1 - 0.05/3) × SE_cost)
power_cost_gate = 1 - Phi[(cost_gate_threshold - Delta_cost) / SE_cost]
```

`Phi`는 표준정규분포 누적분포함수다. 이 식도 VM·저장 비용 분산, 실제 조건 간 상관과 task별 이질성을 측정한 결과가 아니다. 따라서 임의 기대 범위를 승인하더라도 아래 `rho_cost` 보정 전 계산을 최종 표본 수로 쓰지 않는다. 정적 입력 참고값은 어느 선택에서도 총비용 효과크기로 바꾸지 않는다.

최종 구간은 task를 층으로 두고 각 task 안의 반복 block을 다시 뽑는 짝지은 bootstrap으로 계산한다. task 수가 적어 이 방법도 불안정하면 작은 표본으로 확정하지 않고 판정 불가로 남긴다. 관측 차이만 허용폭 안에 있다고 성공으로 쓰지 않는다.

S1·S2·S3 중 하나, 비용 분석 경로, 두 상관의 사전 범위·계획 규칙과 반복 수 계산 방법은 선별 결과를 보기 전에 승인하고 이후 바꾸지 않는다. 비용 추론을 유지하면 사전 기대 절감 범위도 이때 승인한다. 선별 결과가 나온 뒤 새로 확인하는 값은 평가 적격 과제 수 `K`뿐이다. 반복 수는 사전 승인한 식에 `K`를 대입해 정하며, 일정에 맞추려고 성공 기준이나 식을 바꾸지 않는다.

## 차이값의 task 내부 상관과 반복 수 공식 — 승인 대기

과제별 기준선 통과율이 극단적으로 다른 것은 과제 간 이질성의 근거다. 그러나 필요한 상관은 기준선 통과율의 상관이 아니라 같은 task 안에서 반복해 얻는 **압축 조건과 `none`의 차이값** 사이의 상관이다. 압축 비교는 0회이므로 현재 데이터에는 이 차이값이 없고, 아래 두 상관을 직접 추정할 수 없다.

- `rho_quality`: 같은 task의 서로 다른 반복에서 `d_quality = pass_compressor - pass_none` 사이의 상관
- `rho_cost`: 같은 task의 서로 다른 반복에서 `d_cost = (cost_none - cost_compressor) / cost_none` 사이의 상관

두 상관은 같은 값으로 묶지 않는다. 압축할 문자열과 token 감소가 반복마다 비슷해도 품질 결과는 달라질 수 있고, 반대 방향도 현재 자료로 배제할 수 없다. 기존 기준선의 목적 선정 5과제×20회에서 나온 과제별 1/20~20/20 통과율과 `none` 비용 분산은 각각 압축 전 결과이므로 어느 상관의 추정값으로도 사용하지 않는다.

### 사전 범위 후보

아래 범위와 격자는 **측정값이나 추정값이 아니라 승인 전 임의의 민감도 후보**다. 음의 상관을 0으로 잘라 계획하는 것은 양의 상관에서 필요한 표본 수가 커지는 방향을 우선 보기 위한 선택이지, 음의 상관이 불가능하다는 관측이 아니다.

| 지표 | 범위 후보 | 계산 격자 | 범위를 둔 근거 | 성격 |
| --- | --- | --- | --- | --- |
| `rho_quality` | 0.00~0.50 | 0.00·0.05·0.10·0.25·0.50 | 품질 차이는 반복마다 갈릴 수 있다는 작동 가설을 반영해 0부터 강한 양의 상관까지 놓았다. 상한 0.50과 중간값은 자료에서 도출하지 않았다 | 임의의 설계 후보·미추정 |

이 범위를 승인해도 실제 반복 수를 정하는 규칙이 하나 더 필요하다. 두 후보 중 하나를 선별 전에 승인하고 이후 바꾸지 않는다.

| 계획 규칙 후보 | 반복 수 결정 | 허용하는 것 | 한계 |
| --- | --- | --- | --- |
| P1 범위 보호 | 각 범위의 상한을 식에 넣어 두 지표를 모두 만족하는 `R`을 사용 | 승인 범위 안에서 가장 큰 task 내부 상관 보정을 계획에 반영 | 상한에서 유한한 `R`이 없으면 평가 전체가 현재 설계로 판별 불가가 된다 |

현재 범위 후보의 상한을 쓰는 P1은 `K=89`에서도 S1·S2·S3 모두 유한한 `R`을 만들지 못한다. 이는 범위나 성공 기준을 좁히라는 추천이 아니라, 이 범위를 끝까지 보호하면 현재 모집단 크기로 목표 검정력을 보장할 수 없다는 계산이다. P1을 선택하면서 범위를 좁히거나 P2의 계획값을 정하려면 그 값과 근거를 선별 전에 별도로 승인해야 한다.

### 공식 후보

`N_quality,S`와 `N_cost,S`는 선택한 S1·S2·S3의 trial-level 계산값이다. 아래 식은 같은 task 안 차이값의 반복을 독립 trial로 세지 않기 위한 군집 설계효과(design effect) 근사다.

```text
N_eff,m(K, R, rho_m) = K × R / [1 + (R - 1) × rho_m]

R_quality,S(K, rho_quality)
  = max(1, ceil[N_quality,S × (1 - rho_quality)
                  / (K - N_quality,S × rho_quality)])

R_cost,S(K, rho_cost)
  = max(1, ceil[N_cost,S × (1 - rho_cost)
                  / (K - N_cost,S × rho_cost)])

R_S(K, rho_quality, rho_cost)
  = max(R_quality,S, R_cost,S)
```

지표 `m`에서 `K <= N_m,S × rho_m`이면 유한한 반복 수가 존재하지 않는다. 이때 과제를 자동으로 일부 고르거나 문턱을 낮추지 않고 **현재 일정에서 판별 불가**로 보고한다. 이 식은 같은 task 안 차이값의 반복 상관을 근사할 뿐, task별 효과의 분포나 과제 간 이질성을 하나의 값으로 설명하지 않는다. 최종 분석에서 task 동일 가중 paired bootstrap과 task별 효과 분포를 함께 제시하는 이유다.

283·488·1,129는 이 식의 지표별 `N_m,S`를 만드는 trial-level 민감도 계산일 뿐이다. 두 상관과 `K`를 반영하기 전에는 최종 표본 수가 아니다. 15과제×19·33·76회도 일정 비교 예시이며 최종 상한이 아니다.

### 검정력과 판정 불가 위험 민감도

다음 표는 비교를 위해 `K=89`, `R=20`을 고정한 계산이다. 품질은 실제 평균 차이가 0일 때 허용 하한 `-M`보다 낫다고 판정하는 검정력을 계산한다. 비용은 실제 절감이 각 S의 최소 절감과 같을 때 절감 0보다 크다고 판정하는 **증거 조건만** 계산한다. `검정력/판정 불가 위험`은 이 정규 근사 검정력과 `1-검정력`이며, 실제 압축 효과나 결론의 확률을 예측하지 않는다.

| 0.50 | 169.5 | 69.1% / 30.9% | 35.3% / 64.7% |
| 0.75 | 116.7 | 52.0% / 48.0% | 25.0% / 75.0% |
| 0.90 | 98.3 | 44.9% / 55.1% | 21.3% / 78.7% |

**표본·분모:** `K=89`, `R=20`, 조건당 1,780 trial. 품질 분산 0.32, 비용 변동계수 0.525933, Holm 단측 `0.05/3`, 경계 효과에서의 검정력 계산. **성격:** 임의 상관 격자의 민감도 계산이며 측정이 아니다. 실제 짝 안 불일치와 end-to-end 비용 분산이 없으므로 이 비율을 관측 결과의 확률로 읽지 않는다.

비용의 전체 도입 gate는 절감 점추정이 최소 절감 이상이라는 조건도 포함한다. 실제 절감이 문턱과 정확히 같다는 대칭 정규 근사에서는 점추정이 문턱 이상일 확률이 50%이므로, 위 비용 표를 전체 gate의 검정력으로 읽으면 안 된다. 전체 gate의 검정력과 판정 불가 위험을 계산하려면 최소 절감보다 큰 사전 기대 절감 범위가 필요하지만 현재 승인된 값이 없다. 비용 추론 경로에서 이 범위를 정하지 않으면 비용 쪽 최종 표본 수는 계산 불가로 남고, 기술통계 전용 경로를 승인하면 비용 도입 결론을 판정 불가로 둔다.

### 과제 수와 반복 수

총 trial `T=K×R`가 같으면 `N_eff = T/[1+(R-1)rho]`다. `rho=0`이면 과제를 늘리거나 반복을 늘리는 선택의 유효 표본 수가 같다. `rho>0`이면 가능한 한 많은 평가 적격 과제를 먼저 포함하고 task당 반복을 줄이는 쪽이 같은 총 trial에서 유효 표본 수가 크다.

| `rho` | 같은 800 trial에서 `80과제×10회`의 `N_eff` | `40과제×20회`의 `N_eff` | 전자/후자 |
| ---: | ---: | ---: | ---: |
| 0.00 | 800.0 | 800.0 | 1.00배 |
| 0.05 | 551.7 | 410.3 | 1.34배 |
| 0.10 | 421.1 | 275.9 | 1.53배 |
| 0.25 | 246.2 | 139.1 | 1.77배 |
| 0.50 | 145.5 | 76.2 | 1.91배 |
| 0.75 | 103.2 | 52.5 | 1.97배 |
| 0.90 | 87.9 | 44.2 | 1.99배 |

**표본·분모:** 같은 조건당 800 trial을 두 균형 설계에 배분한 예시. **성격:** 군집 설계효과 공식의 계산이며 과제 80개가 적격일 것이라는 추정이 아니다. 실제 규칙은 평가 적격 `K`개를 모두 포함하고, 승인한 식으로 필요한 `R`을 정하는 것이다.

### 사전 고정과 평가 뒤 사용

S1·S2·S3 중 하나, 비용 분석 경로, 두 상관의 범위, P1 또는 P2, 그리고 `R(K, rho)` 계산법을 선별 결과를 보기 전에 승인한다. 비용 추론을 유지하면 전체 gate의 검정력에 쓸 사전 기대 절감 범위도 이때 고정한다. P2를 고르면 두 상관 계획값도 이때 고정한다. 선별 뒤 새로 확인해 식에 넣는 값은 실제 평가 적격 과제 수 `K`뿐이다. 일정에 맞추려고 상관 범위, 계획값, 성공 문턱이나 계산법을 바꾸지 않는다.

평가가 끝나면 관측된 품질 차이값과 비용 차이값으로 두 상관을 각각 계산할 수 있다. 그 값은 사전 주분석의 표본 수, 성공 기준, 신뢰구간이나 판정을 바꾸는 데 사용하지 않고 민감도 분석으로만 보고한다.

## 최종 과제 수와 일정 gate

선별 전에 평가 적격 과제 수를 추정하지 않는다. 선별이 끝나면 기준 B를 통과한 전체 과제 수를 `K`로 두고, 사전 승인한 `R_S(K, rho_quality, rho_cost)`를 적용한다. 유형 분포, 통과율, 실패 위치·category·test ID를 기준으로 일부를 자동 선정하지 않는다.

전체 `K`개 평가의 P90과 Blob 검증·replay·분석·보고 여유가 실제 남은 시간 안에 들어오면 전부 평가한다. 들어오지 않으면 평가를 시작하지 않고 범위 변경 승인을 요청한다. 이 gate는 선별 결과에 따라 평가를 중단할 수 있게 하지만, 성공 기준이나 표본 공식을 사후 변경할 권한은 주지 않는다.

LLMLingua-2 지연은 기존 0.79출현/trial과 5,000자 호출 시간을 새 과제에도 옮기고, 후보 호출을 8개씩 빈틈없이 처리할 수 있다고 가정한 값이다. 과거 79출현 중 31출현이 5,000자를 넘었고 과제별 후보 비중도 달랐으므로 새 선별 과제의 실제 시간은 이 값과 달라질 수 있다. worker 초기화, 후보 도착 간격, image 최초 pull, retry와 한 trial 안에서 후보가 몰려 공통 timeout에 닿는 경우도 포함하지 않았다. 조건별 timeout은 바꾸지 않으며, 압축 지연으로 난 timeout도 해당 조건의 결과로 센다.

### 마감과 보고 여유

최종 마감은 `2026-09-17 21:00 KST`다. 2026-09-14 날짜 기준으로 약 80시간이 남아 전체 계획은 시간상 가능해 보이지만, 전체 89과제의 P90 범위를 확인하기 전까지 이 판단은 잠정이다. 실행 종료 목표는 `2026-09-17 09:00 KST`이며, 그 뒤 12시간을 Blob 무결성 확인, replay 확인, 분석과 보고에 남긴다. 이 12시간은 과거 측정이나 작업량 추정에서 도출하지 않은 **임의의 운영 여유**다.

아래 표는 일정 민감도를 보기 위해 평가 과제를 15개로 가정하고, 그 뒤 평가 실행을 별도로 승인받는 경우만 계산한다. 15과제는 최종 표본 수나 상한이 아니다. 선별에서 평가 중단 gate가 걸리면 평가 시간은 발생하지 않는다.

기존 27.74시간은 표에 표시한 두 자리 수를 먼저 더한 값이다. 반올림 전 산식으로 다시 계산하면 B+S1은 실행 P90 15.7465시간이고, 별도 12시간을 더한 값은 27.7465시간이므로 두 자리 표기는 27.75시간이다. 이 값도 전체 89과제 P90을 확인하기 전에는 잠정 투영이다.

12시간 자체와 이를 검증·분석·보고에 나누는 비율에는 측정 근거가 없다. `6시간+6시간`과 검증을 우선한 `8시간+4시간`은 모두 임의의 운영 후보이며 승인 전에는 확정하지 않는다. workspace replay는 실행 시간 투영에는 없고 이 공동 예약에만 들어 있다.

실제 일정은 다음 산식으로 계산한다. `K`는 선별 뒤 확인한 전체 평가 적격 과제 수, `R`은 선별 전에 승인한 P1 또는 P2와 `R_S(K, rho_quality, rho_cost)`로 계산한 값, 조건 수는 현재 M1의 4개다.

```text
선별 native 시간(q) = ceil(실제 계획 선별 trial ÷ 8) × none trial 시간(q) × 1.4345
평가 native 시간(q) = ceil(K × R × 4 ÷ 8) × none trial 시간(q) × 1.4345
LLMLingua-2 지연(q) = ceil(K × R × 0.79 ÷ 8) × 5,000자 동시 8호출 시간(q)
retry 0회 실행(q) = 선별 native + 평가 native + LLMLingua-2 지연
준비 retry 최대 증가분(q) = ceil(1,780 ÷ 8) × Tprep(q) + ceil(4 × K × R ÷ 8) × Tprep(q)
최악 실행(q) = retry 0회 실행(q) + 준비 retry 최대 증가분(q)
마감 gate 시간(q) = 선택한 실행 경로(q) + 임의의 운영 여유 12시간
```

여기서 q는 P50 또는 P90이고, `Tprep(q)`는 동시성 8에서 provider 호출 전에 실패한 준비 attempt의 벽시계 분위수다. 이 값은 아직 측정하지 않아 준비 retry 최대 증가분과 최악값을 숫자로 제시할 수 없다. 최대 retry 수는 선별 1,780회와 평가 `4×K×R`회다. 모든 첫 attempt가 준비 단계에서 실패하고 fresh 환경의 두 번째 attempt를 시작하는 경계값이며, 품질 실패나 provider 호출 뒤 오류에는 적용하지 않는다.

| 일정 구분 | 조기 종료 | 준비 retry | 현재 제시 가능한 값 |
| --- | --- | --- | --- |
| retry 0회 | 가정하지 않음 | 0회 | 선별 P50 6.7662시간·P90 8.3136시간과 위 `K`, `R` 평가식 |
| 준비 retry 최대 증가분 | 해당 없음 | 선별 1,780회 + 평가 `4KR`회 | `Tprep50`·`Tprep90` 미측정으로 식만 제시 |
| 최악값 | 없음 | 모든 계획 trial에서 F1-R1 1회 | retry 0회 + 최대 증가분. 마감 gate에서는 임의의 운영 여유 12시간을 별도로 더함 |

D1은 진단 기록만 추가하므로 계획 trial 수를 바꾸지 않는다. F1-R1은 준비 오류가 있을 때만 attempt 수와 경과 시간·비용을 늘린다. 조기 종료를 반영한 사후 실제 시간은 완료 trial과 시작된 attempt로 집계하되, 선별 전 일정 적합 판단에는 조기 종료 절감을 가정하지 않는다. 압축기 수나 프로필이 바뀌면 조건 수와 해당 압축 지연 항을 함께 바꾼다.

승인 gate 사이의 대기 시간은 표에 없다. 기준 B를 통과해도 평가 행렬·표본 수·예상 종료 시각을 다시 승인하기 전에는 평가를 시작하지 않는다.

시간이 부족하면 결과를 본 뒤 과제나 반복을 빼지 않는다. S1·S2·S3 선택, 두 상관의 사전 범위·계획 규칙과 `R(K, rho)` 식은 선별 전에 승인하고 이후 바꾸지 않는다. 선별 뒤 전체 `K`개 평가의 P90과 임의의 운영 여유 12시간이 마감에 맞지 않으면 평가를 중단하고 승인을 요청한다. 압축기 조건을 줄이려면 선별 전 별도 범위 변경 승인이 필요하고, 조건별 반복 수를 다르게 줄이지 않는다. 89과제 선별 모집단, contemporaneous `none`과 증거 계약은 유지한다.

- S1·S2·S3 또는 사용자가 정한 다른 품질·절감 기준
- 비용 추론 또는 기술통계 전용 경로. 비용 추론이면 전체 gate의 검정력 계산에 사용할 사전 기대 절감 범위
- M1의 세 도구·프로필과 단일 위치
- `rho_quality`·`rho_cost`의 사전 범위와 P1 또는 P2 계획 규칙
- 같은 task 안 차이값의 반복 상관을 반영하는 `R(K, rho)` 계산식
- 선별 뒤 전체 적격 과제 수 `K`, 공식으로 계산한 반복 수와 예상 종료 시각
- nginx verifier revision
